# ADR-0017：检索能力以工具形式接入（Hybrid Retrieval as a Tool）

- **日期**：2026-10-22
- **状态**：已接受（**未实施**）
- **上游依赖**：ADR-0008（工具调用循环）、ADR-0010（SQLite 持久化）、ADR-0013（分层解耦）、ADR-0004（YAGNI：不引数据库/消息队列的立场，其中「重启丢任务」已由 ADR-0010 修正）
- **下游影响**：`tool.Registry`、`agent.Run` 的上下文预算、`store` 层、`llm` 客户端；后续需 ADR-0018（评测 harness）

## 背景

`agent-engine` 目前只有两个确定性工具（`calc`、`time`），能力边界停留在「能跑通工具调用循环」。
真实 Agent 任务里最常见的一步是「先从自己的知识里找到相关片段，再基于片段回答」，也就是检索。
缺这一层会带来三个具体后果：

1. **能力缺口**：任务只能做无状态计算，无法处理「文档里说了什么」这类问题，工具调用的价值被低估。
2. **招聘口径缺口**：目标岗位族（Agentic AI 基础设施 / AIGC 系统核心）明确要求 RAG 与 Prompt 工程能力，
   而当前仓库的检索命中为零（`grep -ri "embedding|retriev|vector|rerank"` 在源码中无实现）。
3. **可验证性缺口**：即使加了检索，没有对照指标就无法回答「加了之后好在哪」——这会让整块工作退化成
   简历上的形容词。

同时要守住既有取舍：不引消息队列、不引重量级框架、不为一个工具引入新的运行时依赖（ADR-0004 的 YAGNI 立场）。

## 决策

1. **检索是工具，不是服务、不是新项目。**
   在 `agent/tool` 中实现 `search_docs`，注册进现有 `tool.Registry`，由 `agent.Run` 的工具调用循环调用。
   不新增 HTTP 服务、不新建仓库、不引入 LangChain/LlamaIndex 类框架。

2. **索引落 SQLite，复用 `store` 层。**
   新增 `doc_chunk` 表（`chunk_id` / `doc_id` / `source` / `span_start` / `span_end` / `text` / `vector BLOB` / `corpus_version`）。
   索引构建是**幂等命令**（`cmd/index` 或 `-index` 子命令），重复执行结果一致；`corpus_version` 记录语料指纹，
   语料变化未重建时如实报错而不是返回陈旧结果。

3. **混合召回，且禁止静默降级。**
   - 词法：BM25（纯 Go 实现，避免 CGO；中文按字符 bigram 或经 `config` 可配的分词器切分）。
   - 向量：走既有 `llm` 包的 OpenAI 兼容客户端调用 embeddings 端点，模型与维度由配置给默认值。
   - 融合：用 RRF（Reciprocal Rank Fusion）或归一化加权，权重可配，默认词法权重不高于向量。
   - **无 embedding 凭证或调用失败时**，返回 `mode="lexical"` 并在结果与日志中显式标注；
     **不允许**把降级结果伪装成全量检索（这与仓库既有的「禁止静默降级」纪律一致）。

4. **引用回链是硬契约，不是可选项。**
   工具返回 `{chunk_id, doc_id, span:[start,end], score, mode}`，`span` 缺失即视为实现错误（返回参数错误而非空结果）。
   上层回答必须能引用到 `doc_id + span`。没有 span 的检索结果不接受。

5. **受上下文预算约束。**
   召回结果按 token 预算截断（沿用长会话 60% 阈值策略），截断时返回 `truncated=true`，
   并保证被截断的是尾部低分片段而不是头部。

6. **错误必须可分类，供循环层决策。**
   至少三个哨兵错误：`ErrIndexMissing`（不可重试，提示先建索引）、`ErrCorpusStale`（不可重试，提示重建）、
   `ErrEmbeddingUnavailable`（可重试，退化为 lexical 或重试一次）。工具返回值区分「可重试 / 不可重试」，
   禁止把所有失败压成一个 500。

7. **Prompt 版本化。**
   检索结果注入的回答模板放在 `prompts/`，文件名带版本（如 `search_answer_v1.md`），
   模板头部注明用途与改动理由；变体对照结论进评测报告，不在代码里硬编码多套措辞。

8. **完成的定义（DoD，硬门槛）。**
   在 20–50 条任务集上产出**对照表**：`加检索前 vs 加检索后` 的
   任务成功率 / 工具调用正确率 / 引用命中率 / P95 延迟。
   **没有数字就不算完成**——本 ADR 的实施以该表格为验收物，不以「代码能跑」为验收物。

## 候选方案

- **A（采用）**：作为 `tool.Registry` 的一个工具，索引在 SQLite，混合召回 + span 引用。
  复用既有工具循环、trace 与任务队列，一次补齐检索、Prompt、评测三块能力，且不扩大系统面。
- **B**：独立 RAG 服务（单独进程/单独仓库，agent 通过 HTTP 调）。
  缺点：多一套部署与协议，与 ADR-0004 的 YAGNI 冲突；面试叙事上会变成「又一个 demo 服务」，
  与现有运行时割裂。
- **C**：放在防御门禁工程（另一仓库，Python 单机工具）里做，作为规则的历史缺陷召回。
  缺点：与「LLM 用于结构化工程任务」的岗位口径关联弱，且 Python 单机 CLI 撑不起「系统」叙事。

## 后果

- ✅ 工具循环从「两个玩具工具」升级为「带知识面的 Agent」，`trace` 能显示检索步骤与命中片段。
- ✅ 检索、Prompt 版本化、评测三块落在同一仓库，评测可直接复用任务队列与指标层（`metrics`）。
- ✅ 不引入新的运行时依赖，SQLite 复用已有 opt-in 存储。
- ⚠️ embedding 依赖外部 API：需要缓存（同文本不重复请求）与限流，否则成本与 P95 延迟不可控。
- ⚠️ 纯 Go BM25 需要自带切分策略；中英混排语料的分词效果会直接影响召回质量，需在评测里单独观察。
- ⚠️ 索引随语料增长需重建策略（全量重建 vs 增量），首版允许只做全量重建，但必须在文档写明。
- ⚠️ 若评测显示「加检索后成功率没有提升」，按反向判据收口：不把该能力写入对外材料，
  转而把时间投回调度/取消/恢复的深度。

## 非目标

- 不做分布式检索，不引入 Kafka / Redis / 向量数据库服务（沿用 ADR-0004）。
- 不做 Web 前端与多模态检索。
- 不做重排模型（rerank）的独立服务化；首版可用简单规则或直接以融合分数排序。
- 不引入任何 Agent 编排框架。
