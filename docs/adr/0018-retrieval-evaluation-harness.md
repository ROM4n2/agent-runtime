# ADR-0018：检索能力评测 harness（任务集、指标与验收口径）

- **日期**：2026-10-22
- **状态**：已接受（**未实施**，与 ADR-0017 同步实施）
- **上游依赖**：ADR-0017（检索即工具，DoD 引用本文）、ADR-0012（Trace 观测）、
  vault `01-Rules/AGENT-EVALUATION-HARNESS.md`（上位规则，裁剪引用）

## 背景

ADR-0017 的 DoD 要求「加检索前 vs 后的对照表：任务成功率 / 工具调用正确率 / 引用命中率 /
P95 延迟」，但未定义 harness 形态、任务集来源、指标判定方式与报表格式。不先固定这些，
实施时会出现三个可预见的失败模式：

1. **基线不公平**：`agent.Run` 的 `MaxAgentSteps=5` 是硬上限，检索多耗一步就可能把
   检索判成负分；prompt 模板若与实现同步演进，对照即失效。
2. **判定不可复现**：「引用命中率」若靠人肉看 20-50 条，换个评审换套结论；
   LLM-as-a-Judge 表面打分则是 vault 规则明令禁止的。
3. **噪声淹没信号**：LLM 非确定性下，20-50 条任务集上 2/50 的差异就是噪声；
   单次成功率下「无提升」结论等同于抛硬币。

vault 上位规则 `AGENT-EVALUATION-HARNESS.md` 面向重型场景（双控制交互仿真 + 用户模拟器 +
环境物理状态真值）。本场景是「单轮 prompt → 工具循环 → 引用」的轻量对照，
按该规则 §4 边界条款（单业务场景强上重型结构只得样板层）裁剪，保留三条 MUST。

## 决策

### 1. 形态：轻量 CLI harness，一条命令跑完整对照

`eval run [-group baseline|lexical|hybrid] [-repeat N] [-set tasks/retrieval_v1.yaml]`：

- 任务集是 YAML 文件，**入仓先于实现**（PR 里先见任务集，后见检索代码）；
- 每任务独立走既有 `agent.Run` 循环（注入假 LLM 或真实 LLM 由配置决定，默认真实 +
  `seed` 固定 + 温度固定）；
- harness 本身是纯消费者：只调 `agent.Run` + `tool.Registry` + `TraceBuffer`，
  不新增任务队列路径，不碰 HTTP 层；
- 产物：`docs/eval/YYYY-MM-DD-<group>-r<N>.md` 报表 + 机器可读 JSON（逐任务明细）。

任务集条目结构：

```yaml
- id: q001
  prompt: "agent-api 的崩溃恢复标记僵尸任务时写的错误文案是什么？"
  scope: in-corpus            # in-corpus | cross-chunk | out-of-corpus
  expect_docs: [docs/adr/0015-crash-recovery-and-task-rehydration.md]
  expect_spans: [[120, 168]]  # 期望引用区间（程序判定用）；out-of-corpus 题 expect 为拒答/无引用
```

> **修订注记（2026-10-23，Task 9 实施时）**：任务集文件格式由 YAML 改为 **JSON 数组**
> （字段与上表一一对应，snake_case 标签不变，文件后缀随之改为 `.json`，
> 如 `eval/tasks/retrieval_v1.json`）。原因：仓库依赖纪律为「默认零第三方依赖，
> 引入前先立 ADR」（AGENTS.md §3），YAML 解析器不在标准库；自写 YAML 子集解析器
> 有静默错解析风险，代价大于收益。span 口径、判定逻辑与防共谋纪律均不受影响。
> 判定器（`eval/grader.go`）是引用命中的唯一实现，禁 LLM-as-Judge 的决策不变。

防共谋纪律：语料为仓库自有 `docs/` + `README`；题目**先入仓后跑**，禁止跑完挑题；
必须包含 `cross-chunk`（跨分块综合）与 `out-of-corpus`（考察不编造）两类——
纯语料内直答题会让切分器与题目共谋，虚高命中率。

### 2. 三条 MUST（自 vault 上位规则裁剪）

1. **成对受控（单变量）**：baseline / lexical / hybrid 三组 MUST 运行在完全一致的
   prompt 模板版本、`seed`、温度、`MaxAgentSteps` 上限下；同一份任务集；
   每次只开/关一个自变量（检索有无 / mode），指标变动必须能归因到单一自变量。
2. **物理真值判定（禁 LLM-as-Judge）**：引用命中率由**程序判定器**计算——
   实际引用 span 集合与期望 span 集合的**覆盖率**（`|want ∩ ∪got| / |want|`，逐 want 后平均）；
   任务成功 = 结论正确**且**引用命中期望集合。判定器单一实现（`eval/grader.go`），
   禁止第二套口径。
   > **修订注记（2026-10-23，Task 12 实施实证，两处口径修正）**：
   > ① **数据源**：原"从 trace 的 tool_result 解析"不可用——`agent.MaxTraceDetail=512` 是
   > 运行时观测的有界设计（正确且不改），而每个 hit 的 `text`（512 rune 中文 ≈1.5KB）单独
   > 就超限，实测 q009 完整 recall 0.640 → 截断后 0.091。评测改为**包装工具收集完整返回**
   > （`GradeWithHits`），trace 路径仅作兜底。
   > ② **计分**：原"交并比（IoU）"对 chunk 窗口与答案段的口径天然失真——工具返回的
   > `Hit.Span` 是 ChunkSize=512 的窗口，任务集 expect_spans 是答案段落（远小于 chunk），
   > 多个 chunk 拼接完整覆盖答案段时 IoU 仍给 0.091。改为 **per-want 覆盖率**后同一场景为 1.0；
   > `spanScore`（IoU）保留作边界分析但不驱动判定。
3. **首错归因（替代 max-steps 根因）**：失败任务沿 trace 逆推，标定首个偏差步骤，
   三分类：`no-search`（未调用 search_docs）/ `wrong-span`（调用但命中错误区间）/
   `right-span-wrong-reasoning`（命中正确但结论错）。**禁止**把
   `max steps exceeded` 当作失败根因——那 99% 是表层症状。

### 3. 指标定义与噪声控制

| 指标 | 定义 | 噪声控制 |
| --- | --- | --- |
| 任务成功率 | 结论正确且引用命中期望集合的任务占比 | **N=3 重复**，报告中位数 + P25-P75 区间；单次值仅入明细 |
| 引用命中率 | 实际 span ∩ 期望 span 的并交比，逐题后聚合 | 同上 |
| 首错分布 | 三分类计数 | 按组汇总 |
| P50/P95 延迟 | 单任务端到端墙钟 | 同组内取分位 |
| 平均步数 | `trace` 步数均值 | 防「拉长轨迹换通过率」 |
| token 成本 | prompt+completion 累计（llm 侧计数） | 同组对比 |

判定阈值（反向判据）：**N=3 重复下 lexical 组的任务成功率中位数相对 baseline
无统计意义的提升（差值 ≤ 任务集规模的噪声带，取 ±2/|set|）即判「无提升」**——
无提升则**不合入**检索能力，时间转投调度/取消/恢复深度。hybrid 组单独判定。

### 4. 报表格式

`docs/eval/*.md` 固定节：任务集版本与 hash、环境（模型/seed/模板版本/mode）、
三组对照表（上述六指标）、逐任务明细表（id/scope/组/成败/首错分类/命中 span/步数/延迟/token）、
首错归因 Top 3、结论段（合入 / 不合入 + 理由）。明细表是审计与复跑的锚，
禁止只留汇总数字。

## 候选方案

- **A（采用）**：轻量 CLI harness，程序判定器，N=3 重复分布，首错归因三分类。
- **B**：完整移植 vault 重型规则（双控制仿真 + 用户模拟器模型多轮交互）。
  缺点：单轮检索评测上重型结构是过度设计，产出样板层。
- **C**：评测口径并回 ADR-0017 DoD 一节，不独立成文。缺点：违背既定
  「实施前先写 ADR-0018」决策；口径与架构纠缠，演进时互相牵动。

## 后果

- ✅ 验收物是数字与逐任务明细，「代码能跑」不再是完成定义。
- ✅ 任务集入仓先于实现，评测可被第三方复跑（同 seed 同模板）。
- ✅ 首错归因把「检索没用好」与「推理错了」分离，指引优化方向。
- ⚠️ 任务集构造是一次性成本：20-50 条高质量题（含期望 span 人工核定）需在实施首步投入。
- ⚠️ N=3 重复使评测 token 成本 ×3；用假 LLM 跑基线组可降本（判定器只认 span，不认生成质量）。
- ⚠️ 期望 span 的核定本身带人工误差；判定器对边界重叠（span 部分相交）的计分规则
  须在 grader 实现时写死并测试（交/并按 0.5 权重计入，边界案例单测覆盖）。

## 非目标

- 不做多轮对话场景评测（当前任务均为单轮 prompt）。
- 不做用户模拟器与环境物理状态仿真（vault 重型规则全貌不在本项目范围）。
- 不评测 llm 生成质量本身（只评「检索是否被正确使用」）。
